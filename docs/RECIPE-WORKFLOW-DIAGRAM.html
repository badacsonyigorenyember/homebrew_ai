Recipe Builder Workflow

The LLM decides what goes in the beer and why; code decides how much, and checks that the result is the beer that was asked for. The model runs in three steps only (S1, S6, S9). Everything else is SQL or a script, so the numbers can be reproduced and tested.

Watch-outs

Where this kind of pipeline breaks quietly. The numbers match the red markers on the diagram.

Names & input

  1. ⚠ 1
    Validate the Brief, don't trust it. Parse the LLM output against the schema and retry once on failure. Anything the model filled in on its own must be tagged inferred, never passed off as the user's words. S1
  2. ⚠ 2
    Names are messy. “Citra®”, “HBC 394”, “2-row”, “pale malt”, Hungarian names. Match on the alias table first, fuzzy match second; if two candidates tie, ask. Also catch self-contradictions (“use Crystal 60, no crystal malts”) here and ask. S2
  3. ⚠ 3
    No refs row means no maths. An ingredient with no specs can't be calculated. Ask for the specs, or take them from the web with a low confidence flag. Never let the model make them up. S2
  4. ⚠ 4
    Web pages are untrusted input. They can carry instructions aimed at the model. Treat them as quoted evidence for this run only, cite them, and never auto-ingest them into the library. S3

Trends

  1. ⚠ 5
    Small samples lie. Show n on every stat. Below about 10 recipes, fall back to the parent category, and say so in the output. S4
  2. ⚠ 6
    Trends are only as good as the corpus. Normalise units and batch size (g/L, not g), normalise hop use and timing, remove duplicate clones of one recipe, and distrust style labels on scraped recipes. S4 · corpus
  3. ⚠ 7
    The median beer is a boring beer. Trends pull toward the average, so let the user's wishes and the p10–p90 band move choices off the median. A “how adventurous” setting can come later. S4 · S6

The model

  1. ⚠ 8
    Closed menu. S6 may only return ids from the S5 pool. Check this in code after every call, and reject and retry on an unknown id. S5 · S6
  2. ⚠ 9
    The model never does arithmetic. It returns %, g/L, targets and reasons. Grams, gravities and IBU come from S7 only. S6
  3. ⚠ 18
    The writer can't change numbers. Put amounts and specs into the text from the calculation result with a template. The LLM writes the prose around them and must not retype a figure. S9

Calculation

  1. ⚠ 10
    One unit system inside. Pick kg, L, g, °C, gravity points and one colour unit (EBC or SRM, with °L converted on import), and convert only at the edges. Decide whether grist % means by weight or by extract, write it down, and make trends use the same definition. S7
  2. ⚠ 11
    Hops have fine print. Pellet, whole and cryo hops have different utilisation (cryo ≈ half dose). Alpha acid varies by lot, so allow an override. Decide how whirlpool IBU is counted. Tinseth needs boil gravity, so calculate gravity first, then IBU. S7
  3. ⚠ 12
    The balancing item can go below zero. If late hops already exceed the IBU target, or specialty malts exceed the OG target, the bittering hop or base malt comes out ≤ 0. Detect that and send it back to S6 as “wrong ingredients”. S7 → S8
  4. ⚠ 13
    FG is an estimate. It is yeast attenuation adjusted for mash temperature and fermentability (sugar raises attenuation, crystal lowers it). Show it as ≈ and keep the formula in one place so it can be tuned against real batches. S7

Checking & loops

  1. ⚠ 14
    Brewing sanity, not just style ranges. Enough diastatic power when adjuncts are high, a cap on specialty %, a sane BU:GU ratio, and a limit on how many hops and malts a recipe can have. S8
  2. ⚠ 15
    Every loop must end. Auto-adjust stops when inside tolerance (OG ±0.002, IBU ±1) or after 5 passes, because changing gravity moves IBU. Re-selection gets at most 3 rounds, then return the best attempt with its warnings. S8
  3. ⚠ 16
    Agree on who wins. Hard user constraints come first, then style ranges, then soft wishes, then trends. If a user target or a must-have ingredient is off-style, warn; don't fail. S8

Running it

  1. ⚠ 17
    Make every run reproducible. Log the model, prompt version and data snapshot (refs + trends build date) with each run, or a changed answer can't be explained. S10

Proving it works

Build the calculator first and test it without any LLM, using selections written by hand.
